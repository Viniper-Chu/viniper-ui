# ADR-0068：首个实施阶段采用可运行的纵向闭环

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

后续目标已经覆盖会话、Provider、工具、权限、历史、编程、记忆、调度和扩展。若先分别铺完每一层，用户会很晚才拿到真正可用的 Agent；若一次堆叠全部能力，又难以定位失败。用户选择方案 C：先完成一条端到端纵向闭环，再沿同一闭环逐步加深。

## 决策

- 第一条实施主线固定为：`会话 -> 模型 -> 工具 -> 权限 -> Provider 续轮 -> 历史/Token 持久化`。
- 首个业务切片采用 ADR-0026 的编程 P1：显式选择项目，发现目录，搜索并读取项目文件，让模型基于真实工具结果完成回答。
- 桌面端和 CLI 必须通过同一 Runtime、ToolRegistry、PermissionPolicy、Provider history 与 Token ledger；不同入口不能各写一套演示逻辑。
- 每个后续阶段都必须能在上一条纵向闭环上运行和回归，不允许用“模块已经存在”代替消费者级证据。
- P1 通过只代表只读编程闭环；P2 文件修改、P3 终端/构建测试、P4 Git/复核仍须分别实现和验收，完整编程目标不缩水。

## 收益

- 用户能尽早获得一条真正可用、可演示、可诊断的 Agent 路径。
- 工具、权限、缓存和历史问题会在真实组合中暴露，而不是到最后才集成。
- 每一阶段都能形成清楚的 PASS/PARTIAL/UNPROVEN 边界。

## 代价

- 某些横向能力在预览期只完成最小可用范围。
- 同一切片需要同时修改 core、features、platform、renderer 与 tests，必须严格维持依赖方向。

## 与既有决策的关系

- 本 ADR 只决定实施顺序，不缩减 ADR-0005、0026 以及 DESIGN 中的完整目标。
- 第一阶段任务合同负责给出 P1 工具 schema、项目边界、Windows 入口和真实 Provider 验收门。
