# ADR-0051：定时任务固定时区并明确夏令时语义

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

只保存本机显示时间最容易实现，但换时区或导入另一台设备后会产生偏移；只显示 UTC 又不适合普通用户安排“每天上午九点”。用户选择方案 C：每个任务保存自己的时区，界面显示本地时间，并明确夏令时与跨设备行为。

## 决策

### 每个任务保存规范时区

- 新建任务默认使用当前操作系统时区，但定义中保存规范 IANA 时区名称，而不是只保存当前 UTC 偏移量。
- Windows 平台把系统时区映射为 IANA 标识，macOS 直接使用系统时区标识；无法可靠映射时要求用户选择，不能用固定 `+08:00` 冒充完整时区规则。
- 每日、每周和日历式任务以保存时区中的墙上时间为准，例如“Asia/Shanghai 每天 09:00”；间隔任务继续按经过时长计算，不因显示时区改变而重新起算。
- 一次性任务同时保存绝对触发时刻和创建时使用的显示时区，换设备后仍指向同一时刻。

### 夏令时只产生一次逻辑计划

- 春季跳时使计划时间不存在时，该日期在跳时结束后的第一个有效时刻执行一次，并记录“因夏令时顺延”。
- 秋季回拨使同一墙上时间出现两次时，只在第一次出现时执行一次，不为同一任务和本地日期重复触发。
- 每个日历计划点使用“任务 + 本地计划日期/时间 + 时区”形成逻辑身份，继续遵守 ADR-0024 的重叠合并，不能因 UTC 偏移变化生成第二个待执行项。
- 操作系统时区规则更新只重新计算未来计划；已经产生的历史和错过记录保持原始时区与偏移证据。

### 换设备与修改时区

- ADR-0044/0050 导入另一台设备时保留任务原时区，不自动改成本机时区；用户可以明确选择“改为此设备时区”，并在保存前预览接下来三次触发时间。
- 修改任务时区只影响尚未形成计划点的未来触发，不改写历史，也不重算正在运行的 run。
- 桌面与 CLI 共同显示任务时区、下一次触发的本地时间和对应绝对时刻；JSONL 输出使用带时区的标准时间字段。

### 与离线补跑协作

- 时区只决定本应产生哪些计划点；程序退出、休眠或连接失效期间仍按 ADR-0018 合并补跑一次。
- 夏令时顺延或回拨不被标成离线补跑；调度历史分别记录 `dst_shifted` 或正常单次触发。

## 产品表现

- 简单表单默认显示“时区：跟随创建时的系统时区”，高级区可改具体城市/地区。
- 任务卡显示“每天 09:00 · Asia/Shanghai”，而不是只显示难以理解的 UTC。
- 时区或夏令时规则导致下一次时间变化时，显示一次非阻断说明和重新计算后的时间。

## 收益

- 跨时区、换机和夏令时场景可预测。
- 普通用户仍按熟悉的当地时间创建任务。
- 同一日历计划不会在秋季回拨时意外执行两次。

## 代价

- Windows/IANA 映射和时区规则更新需要平台适配与测试。
- 春季不存在时间必须采用顺延语义，可能晚于用户原本设想。
- 导入设备后保留原时区可能与新设备当前所在地不同，需要界面清楚提示。

## 与既有决策的关系

- 细化 ADR-0017/0018/0024 的调度触发、离线补跑和重叠合并，不增加独立后台服务。
- 跨设备任务定义随 ADR-0044/0050 的本地归档迁移，但不自动改时区或启用任务。
- 本 ADR 是后续目标设计；Windows 时区映射、DST 用例、跨设备导入和 macOS 行为均为 `UNPROVEN`。
