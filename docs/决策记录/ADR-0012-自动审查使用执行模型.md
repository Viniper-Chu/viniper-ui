# ADR-0012：自动审查使用执行模型

- 状态：Accepted
- 日期：2026-08-12
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

ADR-0010 与 ADR-0011 已确定自动审查只报告不修复，并按任务实际变化智能触发。下一步需要决定审查使用执行模型、强制使用另一个模型，还是要求用户单独配置审查模型。用户选择方案 A：使用本次执行任务的同一个模型。

## 决策

1. 每次审查使用执行 run 开始时固定的同一 Provider、profile 与 model id。
2. 审查不要求第二个 Provider、第二个 API Key 或额外的模型配置。
3. “同一模型”不等于延续执行对话。审查必须是单独的 Provider 请求，并使用全新的只读上下文。
4. 审查请求只包含：
   - 固定的只报告审查指令与输出 schema；
   - 用户原始目标和明确验收要求；
   - 最终成果或必要摘录；
   - 文件/数据/系统/外部状态差异；
   - 工具结果、确定性检查和外部操作回执。
5. 审查请求不注入执行阶段的隐藏推理、完整对话流水或“为什么我这样做”的自我辩护文本。
6. 原执行模型在审查时不可用、无权限，或受到 Provider 配额、余额、上下文及全局账户限制时，结果标为“无法验证”或“审查停止”；不得静默换成另一个模型。

## 独立性的定义

本方案提供的是“同模型、不同上下文和不同角色”的程序性独立，而不是模型多样性：

- 执行上下文负责规划和行动。
- 审查上下文只看目标、成果与证据。
- 确定性测试和工具证据优先于模型判断。
- 审查没有执行工具和修复权限。

它仍可能继承同一模型的知识盲点和判断偏差，这是用户选择方案 A 的明确代价。

## 缓存与用量

- 固定审查指令、工具说明和输出 schema 放在稳定前缀，动态任务证据追加在尾部。
- 同一模型有利于复用 Provider 连接和稳定前缀策略，但不保证缓存一定命中。
- 审查 Token、Provider 返回的缓存读写和耗时与主执行分开记账；ADR-0059 后不记录金额。
- Provider 未返回缓存数据时显示“未提供”，不能推算成真实命中。

## 产品表现

- 审查状态显示“审查模型：同执行模型”，并可展开查看具体 Provider 与 model id。
- 不增加要求用户选择第二模型的设置步骤。
- 审查结果继续区分确定性检查和模型判断，不因使用同一模型而伪装为独立专家共识。

## 收益

- 配置最简单，只有一个可用模型时仍能完成执行与审查。
- 不需要额外 API Key，也不会因第二个模型缺失阻塞审查。
- Provider 连接、计费理解和稳定前缀缓存策略更统一。

## 代价

- 执行和审查可能具有相同的知识盲点、偏见或格式习惯。
- 同模型的新上下文只能减少锚定，不能提供真正的模型多样性。
- 高质量审查更依赖明确目标、差异、测试和外部回执。
