# ADR-0024：同一任务的重叠周期最多保留一个

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

重复自动任务可能比自身周期更慢，例如每 5 分钟触发一次，但一次运行需要 12 分钟。把每个新周期全部排队会形成越来越长的积压，全部跳过又会丢失最新一次需求。用户选择方案 C：当前项之外最多保留一个合并待执行项。

## 决策

### 一个当前项加一个待执行项

- 本规则适用于间隔、每日和每周任务，以稳定 `scheduleId` 判断同一任务。
- 同一 `scheduleId` 已有 queued 或 active occurrence 时，新正常计划点不创建无限队列。
- 第一个重叠计划点创建一个 `overlap_pending`；之后继续到达的正常计划点合并进该项。
- 任意时刻，同一计划最多存在一个当前 queued/active occurrence 和一个 overlap pending。
- 一次性任务不会产生周期重叠，不适用本规则。

### 合并记录与执行

- overlap pending 记录覆盖的正常计划点数量、最早计划时间和最新计划时间。
- 主 `scheduled_at` 使用最新计划时间，历史仍能展开查看完整计数和时间范围。
- 当前项结束后，只要计划仍启用，pending 项使用当时的最新任务定义、权限与连接进入普通队列。
- pending 项只创建一个实际 run，只执行一次 Provider/工具循环，并至多进行一组自动审查。
- Token、缓存和耗时按一个实际 run 统计；历史另记它覆盖了 N 个正常计划点，不记录金额。

### 当前项如何结束

- 当前项成功后，pending 项按普通队列规则等待显式依赖、实际资源、全局容量和 Provider 容量；同一会话存在别的 run 本身不再构成阻塞。
- 当前项失败或取消后，pending 项仍可执行，因为它代表后续正常周期，不是对失败项的自动重试。
- Provider 临时错误只在当前逻辑请求内按 ADR-0023 总尝试最多 5 次；不会额外制造 overlap pending。
- 当前项仍在等待权限、连接、Provider 重试或自动审查时，也视为尚未结束，后续周期继续合并到同一个 pending 项。

### 暂停、删除与编辑

- 用户暂停计划时，尚未开始的 overlap pending 取消并记录“因暂停未执行”；暂停期间不累计新计划点。
- 用户删除计划时，overlap pending 随计划删除，不再执行。
- 用户编辑计划时，已经存在的 pending 项保留原计划点数量与时间范围，但真正开始时使用最新任务定义。
- pending 项开始后成为新的当前项；其运行期间再次到达的周期重新最多保留一个 pending。

### 与补跑的关系

- overlap pending 是程序运行期间正常周期重叠，不标成离线“错过”。
- 如果同一计划后来同时存在补跑元数据与尚未开始的正常 pending，按 ADR-0022 折叠成一个实际 run，同时保留补跑来源和重叠周期计数。
- 合并不改变原始日历锚点，也不会从实际完成时间重新计算周期。

## 产品表现

- 任务卡显示“等待上一轮结束 · 已合并 N 个计划点”。
- 详情显示最早与最新计划时间，以及当前项处于执行、审查、等待权限还是等待 Provider。
- 历史显示“实际运行 1 次 · 覆盖正常计划 N 次”，不生成 N 个看似分别执行过的成功记录。
- 暂停、删除、失败和取消的结果使用具体文案，不把合并项冒充已完成。

## 收益

- 长任务不会形成无上限积压。
- 最新正常计划仍会得到一次执行机会。
- 高频发送、发布、付款或项目写入不会因积压突然连续执行多次。
- 合并数量和时间范围仍可追溯。

## 代价

- 被合并的每个周期不会分别产生独立结果。
- 若任务持续时间始终长于周期，任务可能长期接近连续运行，但队列长度仍最多为一。
- 当前项失败后，后续 pending 仍可能执行同类外部动作；它属于新的计划集合，界面必须明确区分于失败重试。
