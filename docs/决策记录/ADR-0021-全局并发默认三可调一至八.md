# ADR-0021：全局并发默认三，可调一至八

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

任务可按实际资源冲突智能并行，但仍需要应用级上限，避免大量无关任务同时占用 API、电脑和本地工具。固定为 2 会牺牲并行效率，固定为 4 又可能对普通设备和小额度 Provider 过重。用户选择方案 C：默认 3，并在高级设置中允许 1–8。并行资格最初由 ADR-0020 规定，现按 ADR-0025 执行。

## 决策

### 默认值与设置

- `maxConcurrentRuns` 默认值为 3。
- 设置页“高级”提供“同时运行任务数”，只接受 1–8 的整数。
- 普通用户不需要配置；设置不放在新手首次使用流程中。
- 设置由当前数据根的 Runtime 所有者全局持久化；桌面端与 CLI 客户端通过正式应用服务读取同一个值，不直接双写存储，也不各自获得一套名额。

### 哪些任务占用名额

- 手动任务、跨会话委派和自动任务都进入同一个全局容量控制。
- 一个 run 从真正开始执行到自动审查结束始终只算一个名额；审查不会额外再占第二个名额。
- 正在调用模型、流式响应、执行工具或自动审查的 run 占用名额。
- “等待依赖”“等待资源”“等待空闲名额”、显式等待消息、等待权限和等待连接不占全局名额。
- 等待状态保留进入时间、来源优先级和等待提升记录；恢复实际执行前必须重新取得资源与空闲名额。

### 多个限制如何叠加

- 任务只有在显式依赖、实际资源冲突规则、全局名额和对应 Provider 容量都允许时才开始。
- 不允许任务先占住一个全局名额，再长时间等待依赖或资源锁。
- Provider/profile 明确提供更低并发限制时使用更小值；Provider 未提供时不猜测虚构值。
- 多个 Provider 的任务仍共同受全局 3 个名额限制，同时各自遵守自己的更低限制。

### 运行中修改设置

- 调高上限后立即重新评估排队任务。
- 调低上限不会取消、暂停或杀死已经运行的任务。
- 当前运行数高于新上限时，现有任务继续完成，新的任务显示“等待空闲名额”，直到运行数降到新上限以下。
- 设置变化写入审计事件，但不写入 API Key 或其他秘密。

## 产品表现

- 高级设置显示当前值、合法范围和一句说明：“桌面端与 CLI 共用；Provider 限制可能更低。”
- 自动任务、会话侧栏和 CLI 区分“等待依赖”“等待资源”和“等待空闲名额”。
- 状态详情显示当前并发，例如“正在运行 3/3”，但不把排队任务算作正在运行。
- 排队等待时长与模型/工具执行耗时分开统计。

## 平台说明

- Windows 桌面端和 Windows 原生 CLI 必须遵循同一设置。
- macOS 草案遵循相同合同，不依据 CPU 核心数偷偷改变默认值；真机仍为 `UNPROVEN`。

## 收益

- 默认设置兼顾普通用户的稳定性和多会话并行能力。
- 高级用户可以根据设备、API 额度和任务类型调整。
- 桌面端与 CLI 通过 ADR-0031 的单一 Runtime 所有者共享真实队列，不会绕过彼此重复放大并发。
- 调低上限不会破坏正在进行的工作。

## 代价

- 默认 3 不一定适合所有设备和 Provider。
- 用户设为 8 时可能更快触发 Provider 限流或显著增加同时 Token 与本机资源占用；产品不计算金额。
- Provider 未公开并发限制时，只能在真实限流发生后按 ADR-0023 的有边界重试规则处理。
- ADR-0065 为本地推理增加默认 1 路的独立资源容量门；它与本 ADR 的全局 1–8 上限同时生效，不能放大应用级并发。
