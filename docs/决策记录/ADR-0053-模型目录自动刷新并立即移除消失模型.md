# ADR-0053：模型目录自动刷新并立即移除消失模型

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

只手动刷新容易长期显示已经下线的模型；自动刷新但保留消失模型更有利于旧配置连续性，却可能让用户不断尝试一个 Provider 已明确移除的模型。用户选择方案 B：自动刷新模型目录，模型在成功刷新中消失后立即从当前可选目录移除。

## 决策

### 自动取得当前目录

- Runtime 所有者在 Provider profile 启用后、应用启动后的合理时机和每 24 小时检查一次模型目录；用户也可手动刷新。
- 刷新只调用该 profile 已声明且当前协议支持的官方模型发现端点；没有发现能力的 profile 继续使用用户手工填写的模型，不伪造自动目录。
- 桌面与 CLI 共用最后成功目录、检查时间和错误状态，不重复把同一 profile 当成两套来源。

### 成功刷新后立即移除消失模型

- 只有收到语义有效且成功解析的权威模型列表后，才与上一次成功目录比较；网络、认证、限流、服务错误或解析失败不能被当成空列表。
- 上一次存在而本次成功列表缺少的模型立即从新会话、模型选择器和智能分配候选中移除，不设置额外宽限期。
- 用户手工配置且 Provider 没有权威发现能力的模型不会被自动移除；它只能由用户删除或由该 Provider 后续真实目录明确否定。
- 新出现模型可以进入目录，但能力、缓存和推理档位未确认时标为“能力待确认”，不能凭模型名自动宣称完整支持；ADR-0059 禁止目录维护价格。

### 不改写历史或活动 run

- 已完成 run、消息、Token/缓存账本和审查回执继续保留原 Provider/profile/model id；“从目录移除”不等于从历史记录删除。
- 正在运行的 run 使用 ADR-0028 的冻结模型快照，不因目录刷新中途换模或取消；该 run 结束后，消失模型不能用于新的续跑。
- 仍把消失模型作为会话默认值的会话进入 `model_unavailable`，Composer 禁止开始新 run，并要求用户明确选择替代模型。
- 自动任务和委派任务若引用消失模型，在触发时进入“模型不可用”，不静默改用智能路由或其他 Provider。

### 可见变化

- 模型目录显示最后成功刷新时间；消失模型的会话显示“此模型已不在 Provider 当前目录中”。
- 用户选择新模型时创建新的会话默认快照，不改写旧 run，也不把缓存统计从旧模型合并过来。
- 刷新差异进入结构化事件，但不包含 API Key 或完整鉴权响应。

## 收益

- 当前选择器不会长期保留 Provider 已移除的模型。
- 自动路由不会继续把新任务派给消失模型。
- 历史证据和活动任务仍保持可追溯、不被刷新改写。

## 代价

- Provider 临时从目录隐藏模型时，新任务会立即无法选择它。
- 旧会话需要用户手动选择替代模型后才能继续。
- 每 24 小时刷新会产生少量网络请求，并依赖各 Provider 模型目录质量。

## 与既有决策的关系

- 细化 ADR-0028 的固定模型快照和 ADR-0035 的智能候选；消失模型只从未来候选移除，不触发运行中静默换模。
- 刷新网络遵守 ADR-0023 的错误分类和 ADR-0048 的 profile 网络配置；失败不产生目录删除。
- ADR-0058 的本地模型目录同样不凭名称猜能力；用户明确安装的本地模型不会因云端目录刷新被删除。
- 本地模型权重版本由 ADR-0063 单独管理：可以发现更新，但不会随本 ADR 的云端目录刷新自动下载、替换或切换。
- 本 ADR 是后续目标设计；自动发现、24 小时刷新、消失模型状态和真实 Provider 目录差异均为 `UNPROVEN`。
