# ADR-0025：同一会话任务采用冲突感知智能并行

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

此前规则允许不同会话并行，但同一会话中的手动任务、委派任务和自动任务必须串行。用户指出这些任务应当能够一起进行，并选择方案 C：正常情况下并行，只有实际资源冲突或并发容量满载时才排队。

## 决策

### 同一会话允许多个独立 run

- 手动任务、跨会话委派和自动任务进入同一调度器，均可与同一会话的其他独立 run 同时运行。
- 同一会话不再拥有“同时最多一个 run”的固定互斥；实际并行数量仍受 ADR-0021 的全局默认 3、可调 1–8，以及 Provider 已知上限约束。
- 自动审查属于原 run 的完成阶段，不额外创建一个并发 run 或优先级项。
- 同一 `scheduleId` 的周期重叠仍按 ADR-0024 最多保留一个 pending，不因同会话并行而重复触发同一计划。

### 上下文和结果隔离

- 每个 run 具有唯一 `runId`，在开始时固定自己的会话历史快照、Provider/model、权限、工具与 Skill、项目指令、Token 账本、事件流和取消信号。
- 兄弟 run 的流式文字、工具结果和临时状态不会实时注入彼此上下文，也不能互相取消或修改权限。
- run 完成后，结果以带 `runId`、开始时间和完成时间的独立结果块持久化。之后新建的 run 才能读取这些已完成结果。
- 如果任务确实依赖另一个活动 run，必须建立显式依赖或“等待此任务”；未声明依赖的同会话任务按独立任务处理。

### 工具执行前按实际资源判定冲突

- 模型推理、网页读取、文件读取和其他无冲突步骤可以并行；Harness 不因为它们属于同一会话或同一项目就提前串行化整项任务。
- ToolRegistry 为可执行工具声明 `read`、`write` 或 `exclusive` 访问类型和资源键解析器；Harness 根据已经校验并规范化的工具参数，在真正调用工具前取得资源锁。
- 同一资源的读读操作可并行；读写与写写操作互斥。已知写入不同规范文件路径的任务可以并行。
- 一次工具调用涉及多个资源时必须一次性申请完整资源集合；无法全部取得时不保留部分锁，避免两个 run 彼此卡住。
- Git、范围不明或项目级的变更命令、不能可靠限定范围的项目数据修改使用规范项目路径的独占资源键。明确只读的终端命令可以共享读取资源。
- 桌面控制、外部连接和其他具有单一控制面的工具使用其清单声明的应用、账号或目标资源键。无法可靠识别范围时，扩大到该工具最窄的可信父范围，不扩大为整个 Harness 的全局锁。
- 完全访问只改变批准范围，不改变冲突判定；任何权限模式都不能绕过资源锁和审计。

### 等待与恢复

- run 在执行到冲突工具前进入 `waiting_resource`，界面显示具体原因，例如“等待文件”“等待 Git”或“等待桌面控制”；未冲突的兄弟 run 继续运行。
- 等待资源、依赖、权限、连接或 Provider 重试期间不占全局或 Provider 并发名额。恢复时重新竞争资源与容量，不能预占一个条件再等待另一个。
- 文件或项目资源在等待期间发生变化时，恢复执行前重新读取或校验版本；发现前提已变化则把新事实交还当前 run 重新规划，不盲目覆盖。
- 发生自动审查时，只对本 run 实际修改过的资源保持阻止冲突写入的稳定性保护；其他 run 仍可读取这些资源，并可继续使用不相关资源。审查结束、停止或取消后立即释放。
- 取消一个 run 只释放该 run 持有或等待的资源，不取消同会话的其他 run。

### 只有排队时才使用柔性优先级

- 有空闲容量且资源不冲突时，手动、委派和自动任务立即并行，不先比较优先级。
- 多个可运行任务竞争同一资源或剩余容量时，基础顺序为：手动任务 > 委派任务 > 自动任务。
- 已经运行的任务不被抢占；优先级只决定下一个开始或恢复的等待项。
- 同一优先级按进入等待队列的时间先后处理。
- 每连续等待 10 分钟提升一个优先级，最高提升到手动任务级；达到同级后按最早等待者优先。这样委派任务等待 10 分钟、自动任务等待 20 分钟后都能与手动任务公平竞争。
- 优先级不能绕过权限、显式依赖、资源冲突、Provider 上限或同一计划的重叠合并规则。

## 产品表现

- 同一会话存在多个活动 run 时，顶部显示“正在运行 N 项”，每项使用独立卡片展示输入、流式步骤、Token、状态、停止入口和结果。
- 不把不同 run 的流式文字交错成一条回复；完成顺序可以与开始顺序不同，但每项来源和时间保持清楚。
- 等待项显示“等待依赖”“等待文件”“等待 Git”“等待桌面控制”或“等待空闲名额”，并显示已等待时间；发生优先级提升时显示一次简短说明。
- CLI 使用相同 run id、状态和排队语义，可同时观察多项任务，不把桌面端与 CLI 各自计算成独立容量。

## 与既有决策的关系

- 修订 ADR-0003 和 ADR-0020 的“每个 sessionId 同时最多一个 run”。
- 修订 ADR-0020 的“只要工具快照具有写能力就锁整个项目”，改为工具调用前的实际资源锁；范围不明的变更仍使用项目独占键。
- 修订 ADR-0022 的严格进入顺序：当前只在冲突或满载时使用基础优先级、等待提升和同级先进先出。
- 保留 ADR-0021 的全局默认 3、可调 1–8；保留 ADR-0024 的同计划重叠合并。

## 收益

- 同一会话中的研究、编程、委派和自动任务可以真正同时推进。
- 不同文件或无冲突工具不会被粗粒度会话锁和项目锁拖慢。
- 同一文件、Git、范围不明命令和独占桌面操作仍受保护。
- 手动任务通常更快响应，同时等待提升避免自动任务永久饿死。

## 代价

- 同一会话不再天然等同于一条严格线性对话，界面和存储必须以 run 为单位表达并发结果。
- 两个 run 在相近时间取得的上下文快照可能不同；有先后依赖时需要显式等待。
- 工具必须提供可靠的资源范围元数据；范围未知时仍会退化为较粗的项目或应用级排队。
- 等待中的文件发生变化时需要重新读取或重新规划，完成时间可能增加。

## 后续待定

1. 是否允许高级用户调整 10 分钟的优先级提升间隔；v0.0.1 先保持固定，不增加新手设置。
2. 是否为高成本本地工具增加资源权重；v0.0.1 仍按 ADR-0021 每个实际运行 run 计一个名额。
