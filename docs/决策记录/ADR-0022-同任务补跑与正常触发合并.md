# ADR-0022：同一任务的补跑与正常触发合并

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

自动任务恢复后可能存在一个待补跑项，同时下一个正常计划点也已经到达。补跑优先会推迟当前任务，正常计划优先又可能让补跑长期等待；若两次都运行，发送、发布、付款、删除或项目修改可能短时间重复发生。用户选择方案 C：同一个自动任务合并为一次。不同任务最初按进入可运行队列的顺序处理，现已由 ADR-0025 修订为冲突感知并行与柔性优先级。

## 决策

### 同一自动任务合并

- 以稳定的 `scheduleId` 判断是否为同一自动任务，不用提示词文字相似度猜测。
- 待补跑项处于 pending 或 queued、尚未真正开始时，如果同一 `scheduleId` 产生当前正常触发，将两者折叠为一个实际 run。
- 合并 run 使用当前任务定义、当前权限和当前连接；主 `scheduled_at` 是当前正常计划时间。
- 补跑的逻辑计划时间、错过次数、最早与最晚错过时间、中断原因继续作为关联元数据保留。
- 补跑已经开始执行后不追溯合并；后来的正常触发按普通队列规则处理。
- 本规则只处理“补跑 + 正常触发”，不把多个正常周期彼此静默合并。

### 只执行、计费和审查一次

- 合并项只创建一个 run、一次 Provider/工具循环和至多一组自动审查。
- 外部发送、发布、付款、权限修改、远程删除和本地写入不会因为两个逻辑来源而自动执行两遍。
- Token、缓存和耗时按一个实际 run 统计；历史另记它覆盖了一个正常触发和一个含 N 次错过的补跑项，不记录金额。
- 成功后同时关闭本次正常触发和待补跑项。
- 失败或取消时，一个结果同时关联两个逻辑来源，不自动拆出第二个 run 再试；Provider 临时错误只按 ADR-0023 重试同一个逻辑请求。外部结果未知时不得自动重复高影响动作。

### 不同任务保持隔离并行

- 不建立“所有补跑和正常任务”的全局串行队列。
- 不同任务若会话、项目、全局容量和 Provider 容量均不冲突，可以同时开始。
- 不同任务只有在实际资源冲突或容量满载时才排队；按 ADR-0025 使用“手动、委派、自动”的基础优先级和每 10 分钟提升一级的等待保护，同级按持久进入时间处理。
- 较早但仍在等待权限或连接的任务不会占住名额阻塞已经可运行的无关任务。

## 产品表现

- 队列显示“本次计划 + 补跑（曾错过 N 次）”，不显示两个看似都会执行的任务卡片。
- 详情保留当前计划时间、错过次数、首末错过时间和中断原因。
- 历史显示“实际运行 1 次 · 覆盖正常触发 1 次与补跑 1 项”。
- 成功、失败、取消、审查和外部回执均只出现一组，并能展开查看两个逻辑来源。

## 与既有规则的关系

- ADR-0018 的“每个连续中断区间最多补跑一次”继续有效；本 ADR 只在补跑尚未开始且当前正常触发已经到达时进一步合并。
- ADR-0020 的会话串行、项目写入互斥和隔离并行继续有效。
- ADR-0021 的默认 3、可调 1–8 全局上限按实际 run 计数，合并项只占一个名额。
- 合并不会扩大权限，也不会改变原始日历锚点。

## 收益

- 避免同一任务在恢复时连续执行两遍。
- 当前计划不会因为旧补跑被长期推迟，错过记录也不会丢失。
- 外部高影响动作只产生一次实际执行机会。
- 使用一个真实 run 统计 Token、缓存、耗时和审查，记录更清楚。

## 代价

- 合并后不会分别生成“历史时点版本”和“当前时点版本”的两份结果。
- 必须在历史中同时表达一个实际 run 和两个逻辑来源，数据模型稍复杂。
- 补跑已经开始后无法再合并，极端时间边界仍可能有两个先后执行的 run。
