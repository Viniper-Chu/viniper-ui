# ADR-0033：隔离任务自动形成单个提交，共享目录仅显式提交

- 状态：Accepted
- 日期：2026-08-13
- 决策人：用户 / Viniper Harness 管理层
- 适用版本：`v0.0.1 Preview`

## 背景

编程 Agent 如果从不提交，隔离 worktree 的合并与恢复缺少清楚交付单元；如果在所有工作区都自动提交，又可能把用户原目录中的既有改动或尚未确认的半成品写入 Git 历史。用户选择方案 C：隔离 worktree 通过检查后自动形成一个可读任务提交，原目录或共享工作区只有用户明确要求时才提交。

## 决策

### 隔离 worktree 的默认交付单元

- ADR-0027 创建的隔离 worktree 在确定性检查完成、适用自动审查结束且没有阻断问题后，由原执行编排器创建一个可读的任务提交，再进入可合并状态。
- 默认一个 run 只形成一个最终任务提交，内容只包含该 run 在隔离 worktree 中产生并纳入任务范围的变更；不得夹带其他 worktree、原目录或用户分支中的改动。
- 提交信息使用“任务目的 + 主要结果”的人话摘要，不使用内部 run id 作为唯一说明，也不要求普通用户理解内部引用。
- 检查失败、审查报告具体未解决问题、结果无法验证、变更范围不明确或 worktree 仍有非任务成果时，不创建最终任务提交；保留现场并进入继续修复或人工处理状态。
- 自动审查按 ADR-0010 仍然只读；创建提交是审查结束后的执行动作，不由审查层修改 Git。

### 原目录和共享工作区不自动提交

- `workspaceMode=shared` 或直接使用用户原项目目录时，即使检查通过、审查通过或当前拥有项目/电脑完全访问，也不自动执行 Git 提交。
- 只有用户在任务目标中明确要求“提交这些改动”，或在结果页明确点击提交动作，Harness 才能在重新确认范围后创建提交。
- 显式提交只能包含本 run 能证明拥有的变更。若原目录同时存在用户改动或其他 run 的变更，无法可靠分离时停止并请用户选择，不替用户全量暂存。
- 不自动改写、压缩、重排或合并用户已有提交，不自动创建提交来“整理”脏工作区。

### 合并仍是独立动作

- 隔离任务提交完成只代表形成了可审查、可恢复的交付单元，不代表已经合并到用户目标分支。
- 合并继续遵守 ADR-0027 的基线复查、仓库级资源锁、权限与冲突处理；目标分支变化或冲突时保留任务提交和 worktree，不强行覆盖。
- 合并成功后生成提交与合并回执，交给 ADR-0034 管理受管工作区的回收和七天恢复期。

## 产品表现

- 隔离任务结果显示“检查完成 / 审查结果 / 已形成 1 个任务提交 / 待合并”等独立状态。
- 共享目录结果显示“变更尚未提交”；仅在用户要求时提供“提交本任务变更”，不会用默认大按钮诱导提交所有文件。
- CLI 使用相同规则，并在提交前后列出本任务纳入的文件和检查状态。

## 收益

- 隔离任务有清楚、可合并、可恢复的单一交付单元。
- 用户原目录中的未提交工作不会被 Agent 自动写入 Git 历史。
- 自动审查、提交和合并职责分开，失败位置容易理解和追溯。

## 代价

- 共享目录任务需要用户多一步明确提交，不能自动获得整洁提交历史。
- 隔离任务在检查或审查问题未解决时会保留未提交现场，占用受管空间。
- 一个任务一个最终提交不适合所有高级 Git 流程；用户明确要求其他提交结构时应作为新的任务合同处理。

## 与既有决策的关系

- 细化 ADR-0027 的隔离工作区交付与合并阶段，并服从 ADR-0010 的审查只读边界。
- 完全访问只影响是否需要逐次批准，不赋予 Harness 在共享目录自动提交用户改动的权力。
- 本 ADR 是后续目标设计，当前自动提交与真实合并证据均为 `UNPROVEN`。
