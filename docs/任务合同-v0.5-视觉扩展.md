## 用户反馈与修正目标

旧界面被用户明确判定为“很丑”。主要问题不是单一颜色，而是：层级过平、卡片和状态条过多、内容字号过小、留白失衡、聊天气泡感和仪表盘感过强，主任务不突出。

新界面必须吸收以下优点但不得逐像素复制、使用商标或搬运源码：

- Codex：以项目和独立 Agent 会话为中心的任务切换、长任务指挥台秩序。
- Claude Code：执行阶段、思考、工具调用、耗时、错误和结果的清晰反馈。
- Viniper：成熟桌面端的克制密度、可调侧栏、阅读宽度、Composer 与低干扰浮层。
- 本产品特色：玉青色“平静指挥台”、显式跨会话协作、估算/实际 Token 对账。

## V1 信息架构

### 左侧会话栏

- 约 248–264px，产品名/Preview 标识、项目目录、突出但克制的“新建 Agent”。
- 会话按“正在执行 / 等待中 / 已完成”分组；每项只显示状态点、会话名、单行任务摘要、时间/未读。
- 自动任务、Skills 与插件、设置固定在底部；删除旧版大块说明卡和常驻协作宣传卡。
- 会话隔离、重命名、删除和切换行为不回归。

### 中央 Agent 执行时间线

- 顶部窄命令栏展示当前会话、项目/分支、本地状态、Provider/model、运行状态。
- 正文由“用户任务 → 理解/计划 → 工具调用 → 结果”的时间线组成，不再将所有内容渲染成左右聊天气泡。
- thinking、tool call、tool result、权限拒绝、等待、失败、取消、完成均有紧凑行和人话状态；工具详情默认可折叠，已完成文本不得丢失。
- 最终结果使用清晰结果块，可显示文件/摘要/后续动作；不能伪造不存在的文件、费用或 Provider 结果。
- 空状态只保留“添加 Provider → 选择模型 → 交任务”三个短步骤。

### Composer

- 固定在主区底部的一体化输入框；阴影只用于该区域和浮层。
- 附件/上下文在左；Provider/model、权限模式为底部紧凑控件；运行按钮在右。
- 发送、排队、取消、Shift+Enter、运行中禁止切换上下文等现有行为不回归。

### 右侧上下文栏

- 约 292–312px，可折叠，只显示当前运行的上下文。
- 仅保留“概览 / 协作”两类：本次 Token（估算与实际明确分开）、缓存、执行清单、工具摘要、跨会话收件箱。
- 删除重复的全局状态卡、永久大图表和与当前运行无关的信息。

## 视觉系统

- 字体：`Segoe UI Variable`、`Segoe UI`、中文系统无衬线回退；正文不得使用难读的 8–9px 字号，重要正文建议 13–14px，辅助信息不低于 10–11px。
- 色彩：暖白画布、纸面白、墨色正文；玉青表示主操作/连接，靛蓝表示执行，琥珀表示等待，胭脂表示失败。禁止霓虹、赛博风和大面积装饰渐变。
- 密度：4/8px 节奏；主要间距 8/12/16/24；边框 1px；常规圆角 8–12px；不得给每一段信息套独立大卡片。
- 阴影：只用于 Composer、dialog、drawer/popover；主页面靠分隔线、层级和留白组织。
- 图标：使用一致的线性图标或简单 CSS/SVG 图形；不得使用难读 emoji 充当主要图标，不引入外部品牌标志。
- 状态不得只靠颜色；所有交互保持键盘焦点、ARIA 语义和 reduced-motion。

## 响应式合同

- 1440×900：左会话栏 + 中央时间线 + 右上下文栏同时存在，中央仍是视觉主体。
- 960×720：左会话栏和右上下文栏抽屉化；顶部保留会话入口、当前标题、Provider/状态和更多入口；Composer 与任务时间线完整可用。
- 两个尺寸都不得横向溢出、遮挡 Composer、丢失新建 Agent、设置、自动任务、Skills/插件、协作和停止入口。

## 实现边界

- 复用当前 Electron + TypeScript + 原生 DOM/CSS，不新增第二套 UI 框架。
- 按 renderer 功能域拆分时间线、会话栏、上下文栏、Token 和工具状态；不得把新界面全部塞回 `app.js` 或单个 CSS 巨文件而不形成可复用组件/Token。
- 真实 canonical snapshot 是唯一业务数据源；参考图中的示例 Token、费用、文件名和 DeepSeek 状态仅用于版式，不能硬编码为真实运行结果。
- Provider 设置仍使用“国外模型 / 国内模型 / 国内平台 / 自定义”与初学者主路径；低频连接配置继续放 dialog/route，不挤入主工作区。
- 不触碰 Viniper，不读取或复制其用户数据、会话、配置、密钥和安装文件。

## Visual Ralph 验收

每次主要视觉修改后：

1. 使用真实构建和新的 Preview 数据根启动应用，禁止用静态假 HTML 代替应用。
2. 捕获当前 1440×900 真窗口截图，和批准稿形成结构化 verdict：`score`、`verdict`、`category_match`、`differences[]`、`suggestions[]`、`reasoning`。
3. `score < 90` 时根据差异继续修改；不得凭主观感觉宣称完成。
4. 像素 diff/overlay 只作为定位辅助，不替代视觉 verdict。
5. 另做 960×720 真窗口功能/溢出验收；窄窗不要求逐像素匹配 1440 稿。
