## 3. 必须保持的产品边界

- 一个 Runtime owner、一个 SQLite 真源、一个 ToolRegistry、一个 PermissionPolicy、一个 Token/cache 账本；桌面、CLI、调度、workflow、subagent 都是同一 application port 的消费者。

- 模型不能修改 Harness 自身：不提供修改应用源码、系统指令、权限规则、凭据、ToolRegistry 或当前能力方案的工具。模型只能提出“下次运行能力草案”，必须经用户确认。
- 完全访问、自动审查、执行策略继续是三个独立维度；完全访问不自动信任插件，也不绕过禁止自修改、秘密和审计边界。

## 4. CP1：能力组合编译器与冻结运行上下文

新增独立 `core/composition-contracts`、`features/composition` 及镜像 renderer/test：

- 能力贡献至少覆盖 `tool / skill-source / prompt-section / interceptor / workflow / model-provider / semantic-navigation`，声明 id、版本、来源、host/session scope、required、conflicts、before/after、信任与权限需求。
- `CompositionCompiler` 以确定顺序编译并返回可解释结果：enabled、blocked、reason、order、presentation、revision。缺依赖/冲突/环/宿主不兼容必须零激活；不以异常崩溃或静默忽略替代诊断。
- 注册返回 disposer；卸载只撤销该来源贡献。活动 run 保留冻结版本，新 run 才看见变更。
- 预设至少有 `standard`、`deepseek-efficient`、`minimal`、`custom`。standard 与 deepseek-efficient 都保留编程；minimal 只是减少非必要能力。自定义方案可复制、排序、启停、保存和恢复默认。
- 建立单一 `FrozenRunContext`：runId、sessionId、provider/model、composition revision、tool descriptors、Skill 正文/版本、extension snapshot、项目指令、权限/审查、cache profile、workflow/steering 入口。Provider request、ToolLoop、恢复、审查和 UI/CLI 都只读它，不再各取一份易漂移快照。

CP1 门：依赖、冲突、顺序、disposer、旧 run 冻结、崩溃恢复、桌面/CLI 同计划、缓存稳定与禁止自修改测试全绿。

## 5. CP2：生命周期拦截、运行中消息与兼容 Hook

- 新增 typed lifecycle：`run/pre-step`、`provider/pre-request`、`tool/pre-execute`、`tool/execute`、`tool/post-execute`、`tool/result`、`run/pre-stop`、`run/completed`。每个拦截器有来源、顺序、作用域、可撤销注册与明确 decision；拦截和改写进入 canonical event。
- PermissionPolicy、输入校验、资源锁和 ToolRegistry 仍是权威执行边界；插件只能在允许阶段贡献窄决策，不能直接写数据库或执行工具。
- 增加 `steer(runId,message)` 与 `inject(runId,context)`：steer 可唤醒/在下一 step 注入用户方向；inject 不唤醒空闲 run，只在下一 pre-step 消费。二者有 queued/claimed/delivered/rejected/cleared 回执，取消可选择保留或清空 inbox。
- 提供 Claude/Codex 风格 Hook 的声明式兼容层，但只能通过受管插件进程、白名单事件与结构化输入输出；默认无 Hook，故障不带崩 Runtime。

CP2 门：事件顺序、短路、撤销、故障隔离、steer/inject 时序、跨 run 隔离、重启恢复和 UI/CLI 回执全绿。

## 6. CP3：DeepSeek 高效 Code Mode

- 新增一次性 worker-thread code runtime 与保留工具 `run_code`，提供 `native / code / both` 三种工具呈现。DeepSeek 高效方案默认 `both`；用户可固定，run 中不得静默切换。
- 根据本 run 冻结工具生成确定性 TypeScript/JavaScript SDK。程序无 Node fs/process/network/module 入口，只能调用 SDK；但不得把 worker 宣称为安全沙箱，真正权限仍由每个 SDK 子调用的 ToolRegistry/PermissionPolicy 决定。
- SDK 子调用支持有界并行和独占屏障，默认并行 4、允许 1–10；每个 callId、父子关系、权限、artifact、Token 关联、stdout/stderr、错误和取消均可追溯。普通副作用不伪造回滚。
- 输出有字节与条目上限；完整允许输出进入受管 artifact，模型接收有界结果。run 结束/取消必须停止 worker、拒绝新子调用并排空已启动调用。
- 只有 `code` 模式可禁止模型直接调用普通工具；`both` 下两条路径都合法。`run_code` 不能被插件覆盖或卸载。

CP3 门：真实项目读取/编辑/测试的 batch 程序、并行/独占、批准/拒绝零副作用、取消、超限、worker 崩溃、旧工具快照、CLI JSONL 与桌面时间线全绿。

## 7. CP4：语义代码导航、工作流与子 Agent 融合

- 新增 `features/lsp` 的 provider seam，只公开 definition/references/implementation/hover。先交付 TypeScript/JavaScript 本地 provider；语言服务不可用时回退现有 ProjectIndexService 并标记 `fallback`，不得返回伪语义结果。
- LSP 只操作用户明确项目，遵守凭据/越界排除、资源节流、取消和受管进程边界；不提供原始 JSON-RPC 工具。
- 新增 `features/workflows`，支持 prompt chaining、routing、parallelisation、orchestrator-workers、evaluator-optimiser 五种模式。步骤必须调用 canonical tool/run/delegation，不嵌入第二 Provider loop。
- workflow 定义、revision、输入输出 schema、步骤状态、重试/取消、权限、Token 与 artifact 持久化；恢复时只重放未知步骤。子 Agent 使用现有 CoordinationService、全局并发 1–8 和资源锁，父会话只接收结构化回执，不共享私有历史。

CP4 门：四个语义操作、fallback、五种 workflow、子 Agent 容量/取消/权限/Token、恢复和桌面/CLI 直接消费者全绿。
